# Compatibility and Roadmap

RustMQ 0.1.0 is not a complete EMQX 5.8.9 rewrite and is not configuration-, API-, or plugin-compatible with EMQX. EMQX 5.8.9 contains about 369,000 lines of Erlang and more than 100 applications; this release deliberately implements a tested broker core first.

## Durable single-node mode

Durability is opt-in with `[persistence].enabled = true`; the default remains memory-only. Schema version 5 uses redb tables `sessions`, `retained`, `wills`, `api_keys`, `bans`, `dashboard_users`, and `meta`; version 2, 3, and 4 databases are migrated in place by adding the missing empty security-control tables, while version 1 databases remain rejected. Canonical records are versioned JSON DTOs rather than serialized runtime structs, and per-key monotonic revisions/tombstones prevent a delayed snapshot from overwriting a newer put/delete. One bounded writer thread owns redb transactions; no redb type appears in the Broker API. This logical command/DTO boundary is intended to remain reusable by future OpenRaft/RocksDB implementations.

Recovery completes before listeners bind. RustMQ validates record keys, revision namespaces, session state combinations, packet identifiers, QoS/phase relationships, topics/filters, Will ownership/generations, API-key names/public-key derivation/salted-hash lengths/uniqueness/timestamps, Dashboard usernames/roles/auth epochs/bounded Argon2id PHC parameters, ban kinds/canonical IP/CIDR/regex values/timestamps, and epoch-to-monotonic deadline conversion; unknown, inconsistent, exhausted, or corrupt durable state fails startup instead of being repaired. Normal expiry pruning remains allowed. Persisted online sessions are treated as connections terminated by process crash: expiry zero is tombstoned immediately, finite expiry uses `last_alive_epoch_ms + interval` as an absolute deadline so downtime is deducted, and `u32::MAX` remains non-expiring. `last_alive_epoch_ms` is refreshed by critical persisted session mutations (including register, expiry changes, unregister/finalize, subscriptions, queues, and QoS phase changes); it is a conservative last-persisted-activity boundary for one node, not a cluster heartbeat or an exact crash timestamp. Offline finite sessions always carry an explicit deadline.

Recovery revalidates restored control subscriptions against the startup ACL for their stored principal, rebuilds routing buckets, converts residual active Wills atomically to pending Wills, then fires overdue/firing Wills and arms future deadlines. An active Will's recovered fire time is the earlier of `last_alive_epoch_ms + Will Delay` and a finite session-expiry deadline. QoS 1 Ack and QoS 2 Rec inflight entries replay as DUP PUBLISH with the same packet ID; QoS 2 Comp entries replay as PUBREL even if their original application-message expiry elapsed. Retained tombstones and expired retained values are not replayed. A later non-clean CONNECT inherits a session only when its authenticated principal exactly matches the stored owner.

Only `DeliveryTarget::Control` state is durable. QUIC data-stream subscriptions, inflight messages, queues, connection/stream identities, topic aliases, per-connection sent flags, shared-subscription cursors, routing buckets, channels, metrics, authorization caches, and connection tokens remain ephemeral and are neither restored nor silently downgraded to the control stream. Inbound QoS 2 pending/complete state also remains connection-local and is not restart-durable.

With `sync = true` (the default), each critical Broker mutation waits for an Immediate redb commit after releasing in-memory map guards and before the corresponding success ACK/first outbound send/retained publish return. On Tokio's multi-thread runtime, the bounded-channel send and standard ACK wait run inside an explicit blocking boundary so Tokio can compensate with another worker; current-thread and non-runtime callers execute the same synchronous API directly without invoking `block_in_place`. A network packet may have been sent while its later MQTT ACK has not yet committed, so recovery can retransmit it; the guarantee is at-least-once, not exactly-once.

A successful CONNECT persists the online session and active Will before CONNACK. Normal DISCONNECT clears the active Will in the durable finalize transition; abnormal finalize atomically changes the session to offline (or tombstones zero expiry) and writes the pending Will. CONNACK write failure uses the same abnormal path. Administrative DELETE is distinct: command enqueue is generation-fenced, MQTT 5 receives `DISCONNECT 0x98` while MQTT 3.1.1 closes directly, finalize immediately publishes the observed generation's active Will, and session/subscription/inflight/offline/pending-Will state is durably tombstoned before the HTTP acknowledgement. A replacement generation admitted after that enqueue is not removed by the old finalize. Pending Will publication has one force-fire state machine for timers, recovery, same-principal clean-start, and administrative finalization: the durable record is changed to `firing`, the publish path completes, and only then is it tombstoned. A crash can therefore duplicate a publish but cannot silently lose a committed pending/firing Will; stale generation timers cannot fire a replacement Will. Ordinary resume cancellation and principal-owner mismatch may tombstone without publishing. Will Message Expiry starts when the Will is actually published.

With `sync = false`, ordinary broker commands use Eventual durability; API Key, ban, and Dashboard user security-control mutations remain acknowledged and Immediate because stale credentials or access rules are a security failure. Graceful shutdown issues an Immediate flush barrier, but an unexpected process or host crash has an unbounded-by-time RPO for ordinary broker state up to the writer/backend state not yet made durable. Eventual mode relaxes only crash RPO. The first known hard writer transaction or flush error is logged and immediately aborts the process, including for commands without ACKs, so the broker cannot continue successfully handling protocol traffic after detected storage failure.

Database open/corruption errors, unknown schema versions or metadata namespaces, invalid record invariants, exhausted revision/generation namespaces, empty paths, zero writer capacity, and writer transaction/flush failures fail closed. Runtime revision exhaustion and hard writer errors terminate the process. This is single-process, single-node durability—not replicated storage, cluster heartbeat/failover, or complete EMQX persistence equivalence.

## Known P0 limits

- Durable restart state is optional and single-node only. When disabled, outbound QoS 1/2 state, offline queues, sessions, retained messages, pending Wills, dynamic API keys, bans, and Dashboard users remain memory-only. When enabled, control-target broker state, dynamic API keys, bans, and Dashboard users are stored; QUIC data-stream state and inbound QoS 2 pending/complete state remain intentionally ephemeral.
- MQTT 5 Session Expiry, Receive Maximum, Message Expiry, Will Delay/Expiry, subscription NL/RAP/RH, Subscription Identifier, bidirectional Topic Alias, and Enhanced Authentication are implemented. Enhanced Authentication currently has one built-in method, `PLAIN`, backed by the global `[auth]` username/password pair. AUTH Reason String and User Property values are strictly validated and accepted but are not exposed to authentication providers or otherwise used; general reason-string semantics are not implemented.
- Offline queues contain QoS 1/2 messages and are bounded/drop-oldest. They are restart-durable only for control targets when persistence is enabled.
- Retained messages and principal-bound control sessions are restart-durable only when persistence is enabled; otherwise they are lost on restart.
- No certificate-to-MQTT-principal mapping, certificate revocation checking, certificate hot reload, WSS, rate limiter, automatic/flapping ban generation, or dynamic listener API. QUIC client-certificate verification is transport admission only. QUIC 0-RTT follows TLS 1.3 replay semantics and therefore does not itself guarantee exactly-once application effects; it is disabled for mTLS processing until the full handshake authenticates the client.
- Authorization is a static, in-process TOML source compiled once at startup. It intentionally does not implement EMQX regular-expression/CIDR rules, client attributes, certificate-CN subjects, dynamic authorization sources, hot reload, or authorization management APIs. Rule order is first-match rather than deny-overrides. Dedicated authorization allow/deny metrics are not yet exposed; existing broker metrics remain unchanged.
- Publish authorization runs after inbound Topic Alias resolution and before retained/routing or QoS 2 pending state. `${principal}` and `${clientid}` substitutions are accepted only as literal topic-level content: values containing `/`, `+`, `#`, or NUL make that template rule not match instead of contributing MQTT filter syntax. Subscribe authorization removes `$share/<group>/` for matching and requires the configured allowed filter to contain the entire requested filter language; wildcard intersection is not sufficient. Ignore mode returns MQTT 5 reason 0x87 for an ACL denial (or MQTT 3.1.1 SUBACK 0x80) without mutation. An invalid requested filter is not an ACL denial: it returns MQTT 5 Topic Filter Invalid 0x8f (or MQTT 3.1.1 SUBACK 0x80), does not install a subscription or read retained messages, and does not trigger `deny_action=disconnect`; other valid, allowed filters in the packet still succeed. Disconnect mode skips invalid filters during its ACL-denial preflight, but atomically rejects a mixed SUBSCRIBE and terminates the whole logical QUIC connection when any filter is genuinely denied by the ACL. Authorized sessions bind the explicit principal or anonymous identity, so a different identity reusing a client ID starts with `session_present=false` and cannot inherit subscriptions, inflight/offline messages, retained replay, or pending Will state.
- Shared subscriptions are local-node only. Selection retries for a concurrently disappearing subscriber are not implemented.
- Static username/password authentication is global. MQTT 5 Enhanced Authentication supports only SASL `PLAIN` data (`[authzid]\0authcid\0password`) through that same credential pair; because `PLAIN` transmits reusable credentials, use it only over TLS or QUIC (WSS is not currently available). An explicit method is rejected when the pair is unavailable, partial configuration fails closed, and each username/password component is limited to 1024 bytes. Initial Enhanced Authentication has an absolute 15-second deadline by default, configurable with `[auth].timeout_ms` or `RUSTMQ_AUTH_TIMEOUT_MS`; client traffic does not refresh it. `PLAIN` issues at most one no-data challenge, including during reauthentication. There is no per-user database. Static authorization uses only the authenticated principal and MQTT client ID; successful reauthentication to a different principal disconnects with 0x87 instead of changing an active connection's identity.
- Management API is intentionally small and is not compatible with EMQX Dashboard APIs.
- Multi-node cluster behavior is not implemented; `cluster.rs` is an interface and owner-selection boundary only.

## EMQX 5.8.9 core-parity gaps

“P0 implemented” above means the first runnable RustMQ milestone. It does **not** mean parity with the EMQX core feature set. A stricter EMQX-compatibility baseline still has these gaps:

| EMQX-visible behavior | RustMQ 0.1.0 status |
|---|---|
| MQTT 5 Session Expiry, Assigned Client Identifier, Receive Maximum, User Property and reason-string semantics | Session Expiry and Receive Maximum are implemented in memory; the other listed semantics are not implemented |
| MQTT 5 No Local, Retain As Published, Retain Handling and Subscription Identifier | Implemented, including merged identifiers for overlapping subscriptions and retained delivery |
| MQTT 5 Topic Alias | Implemented per connection in both directions, including advertised/configurable inbound maximum, client-advertised outbound maximum, alias reuse, limit validation, and protocol error reason codes |
| Outbound QoS 1/2 inflight state, DUP/PUBREL retransmission, reconnect replay and finite offline queue | QoS 1/2 are implemented with bounded drop-oldest queue; optional single-node restart durability covers control targets only |
| Inbound QoS 2 EMQX timing | RustMQ routes on PUBREL; EMQX 5.8.9 may publish on first PUBLISH and track `awaiting_rel`, so timing is not identical even though RustMQ guarantees route-once |
| Session expiry, queued delivery while offline and expiry GC | Implemented with lazy runtime GC and startup pruning; optional single-node persistence covers control-target state |
| Will Delay and Will Message Expiry | Implemented, including reconnect cancellation, takeover, session-expiry interaction, DISCONNECT 0x04, and optional at-least-once pending-Will recovery |
| Retained Message Expiry and Retain Handling 0/1/2 | Implemented with lazy runtime cleanup, startup expiry pruning, and optional single-node persistence |
| Publish/subscribe ACL and authentication/authorization failure metrics | Static ordered first-match publish/subscribe authorization is implemented for principal/client ID, topic filters/exact topics, templates, QoS and retain. It is enforced for Will, aliases, QoS 2, mixed subscriptions, all transports and QUIC data streams; dedicated authn/authz metrics and dynamic sources are not implemented |
| Limits for ClientId/topic length, subscriptions, inflight, queue, connection count and rate | Packet-size, outbound channel, inflight, and offline queue limits are implemented; the others are not |
| Full malformed-frame and UTF-8 validation matrix from `emqx_frame_SUITE` | Partial validation only; not yet differential-tested against the full EMQX corpus |
| EMQX-compatible `/api/v5` clients, subscriptions, publish, stats and metrics APIs with OpenAPI/authentication | A focused single-node core is implemented: public `/status` and `/api/v5/status`; optional public Dashboard login with in-memory sliding Bearer sessions; Basic- or Bearer-protected clients/kickout/client subscriptions, global subscriptions, publish/bulk publish, retained messages, nodes, stats and five real metrics. This is not full EMQX compatibility |
| EMQX-wide packets/bytes/messages/acked/authn/authz statistics | `/api/v5/metrics` exposes only the five real RustMQ values: accepted/current connections and published/delivered/dropped messages; absent EMQX metrics are not fabricated |
| Shared-subscription failure retry, NACK/redispatch and multiple selection strategies | Local online round-robin only |
| HOCON configuration and EMQX `listeners`, `zones`, `broker`, `stats` schema compatibility | Not implemented; RustMQ uses its own TOML schema |
| 1,000-client/10-minute mixed-QoS soak and full EMQX differential suite | Not run; current evidence is the checked-in functional suite, including WebSocket, QUIC resumed 0-RTT control/data-stream continuation, UDP-address migration, control/parallel-data-stream coverage, stream-affine duplicate subscriptions/delivery/QoS ACKs, cross-stream unsubscribe isolation, stream-level fault isolation, trusted/missing/untrusted TLS and QUIC client-certificate handshakes, and TCP/container smoke tests |

These are compatibility requirements for later milestones, not claims about the current binary. The detailed source references are the EMQX `emqx_frame`, `emqx_channel`, `emqx_session_mem`, `emqx_shared_sub`, `emqx_retainer` implementations and their Common Test suites.

### Management API compatibility boundary

Implemented endpoints are `GET /status`, `GET /api/v5/status`, login/logout, Dashboard user list/create/update/delete/change-password, API Key list/create/get/update/delete, banned list/create/delete/clear, clients list/get/delete and bulk kickout, per-client subscriptions/subscribe/unsubscribe, global subscriptions, publish and bulk publish, retained list/get/delete/clear, nodes/node stats/node metrics, aggregate or per-node stats, and aggregate or per-node metrics.

The management layer is single-node. `/status`, `/api/v5/status`, and the optional `/api/v5/login` route remain public; every other `/api/v5` result, including fallback 404 and method 405, is inside the authenticated router. Protected routes accept the independent Basic API key or an enabled Bearer session. The configured Dashboard pair bootstraps one protected default administrator when absent; subsequent user APIs operate on a local `DashMap` directory and persist through the metadata command boundary when redb is enabled. Usernames and passwords follow the EMQX CE validation rules, while stored human passwords use fixed Argon2id parameters instead of EMQX's fast SHA-256 hash. CE exposes only the administrator role and omits role/backend response fields. Login performs Argon2 verification in a blocking worker and issues a CSPRNG-generated 256-bit opaque token. Successful Bearer authentication applies EMQX-style sliding expiry; each session carries the user's role and persisted authentication epoch. A password change increments that epoch and deletion removes the user, so every old token fails with `BAD_TOKEN` on its next request without a token-table scan. Description-only updates preserve tokens. The configured default administrator and current Bearer owner cannot be deleted. Dashboard user collection/item routes, logout, and API Key CRUD reject Basic credentials with `API_KEY_NOT_ALLOW`; change-password remains available to Basic when the old user password is supplied. Bearer sessions remain process-local and all tokens become invalid after restart. Session count is bounded. Bearer-managed API Key CRUD supports the EMQX name format, 100-record limit, enable and RFC 3339/infinity expiration fields, one-time secret disclosure, and deterministic 16-hex public keys. Only salted SHA-256 secret digests are stored and compared in constant time. Static and dynamic Basic credentials cannot manage API keys (`API_KEY_NOT_ALLOW`). Dynamic authentication uses a local `DashMap` public-key index; mutations are serialized, persisted with per-name revisions when redb is enabled, and can later be routed through a replicated metadata proposal without changing the HTTP/authentication layer. Bearer sessions remain process-local and all tokens become invalid after restart; Dashboard users are persisted when redb is enabled and are not replicated. Dynamic API keys are durable only when persistence is enabled and are not replicated. Bans support exact client ID, CONNECT username and peer IP plus Rust-regex client ID/username and IPv4/IPv6 CIDR rules. Exact checks use `DashMap`; compiled rule sets are atomically published through `ArcSwap`, so CONNECT does not acquire the mutation lock or compile input. All TCP, TLS, WebSocket and QUIC control connections check the original CONNECT username and transport peer before authentication and again before session registration. MQTT 5 receives Banned `0x8A`; MQTT 3.1.1 receives code 5. Creating an exact client ID ban sends an online MQTT 5 client administrative disconnect `0x98`; other ban types affect the next CONNECT. Absolute `until` uses strict `until > now` validity, and expired records are lazily removed during list operations. Ban mutations use per-entry revisions and Immediate persistence when redb is enabled; they remain local and memory-only otherwise. Deferred compatibility includes enterprise viewer/publisher/custom roles and SSO, API-key bootstrap files/roles, automatic/flapping bans, publisher-message filtering, multi-node RPC, OpenAPI, complete EMQX client/metric fields, EMQX config APIs, and advanced client queue/cache interfaces. Client and retained timestamps are epoch milliseconds rather than RFC 3339; HTTP has no native TLS. Admin subscribe/unsubscribe requires the currently online client generation and returns `CLIENTID_NOT_FOUND` for an offline durable session. Administrative DELETE waits for the observed connection generation's durable discard; bulk kickout applies the same rule per item and reports an internal failure as `500 UNKNOWN_ERROR`. JSON publish is trusted and bypasses MQTT ACL checks. A publish with no matched subscription returns 202 `no_matching_subscribers` even if its retained value was stored; a matched publish returns 503 `failed_to_dispatch` when neither a live send nor a durable queue accepts it, or 200 with only `{id}` after acceptance. Bulk publish validates the entire request before routing any item and chooses overall status in 503, 202, 200 precedence. The outcome name `accepted` includes a successful send or durable queue admission and is intentionally not described as delivered; Broker delivery metrics retain their existing meaning. Shared-subscription `match_topic` evaluates the parsed underlying filter while `share_group` remains an independent predicate, including MQTT `$SYS` wildcard rules. Clients, subscriptions, and retained lists clone and sort only a bounded filtered snapshot, reject page arithmetic overflow with 400, return `503 RESOURCE_LIMIT` when `management.max_page_limit` is exceeded, and share four concurrency permits. Retained payloads are base64 in detail responses and omitted when larger than 1 MiB.

## P1

- Certificate reload/principal mapping, WSS, remaining MQTT 5 property semantics, and additional EMQX QUIC differential coverage.
- Enterprise viewer/publisher/custom roles and SSO, API-key bootstrap files/roles, automatic/flapping bans, multi-node management RPC, OpenAPI/config APIs, complete client fields, and advanced client queue/cache management.
- Replicated durable sessions/retained messages/pending Wills/queues and migration tooling beyond the single-node schema.
- OpenRaft metadata group, RocksDB state, partition ownership epochs, node forwarding, static cluster formation.
- Trie/radix topic index, per-tenant quotas, dynamic authorization sources/hooks and HTTP/JWT authentication.
- Client/session/subscription management APIs, tracing, OpenTelemetry, load and soak benchmarks.

## P2

- SWIM/DNS/Kubernetes discovery, online resharding, replicated data partitions, disaster recovery.
- Rule engine and connector SDK; HTTP, Kafka, SQL, object-store, and cloud integrations as independent plugins.
- MQTT-SN, CoAP, LwM2M, STOMP, and other gateways.
- Dashboard, RBAC/SSO, schema registry/validation, message transformation, audit, rebalance tooling.

Enterprise EMQX applications marked with `BSL.txt` were excluded from implementation reference. Equivalent future capabilities must be independently designed or used under their applicable license.
